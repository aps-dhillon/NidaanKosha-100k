PART 1: WHAT WE WISHED TO DO
================================================================================

THE BIG PICTURE
---------------
We wanted to build a complete data science pipeline on the NidaanKosha-100k
dataset (100,000 Indian patients, 6.8 million lab readings) that would:

  1. Ingest and clean real-world medical data at scale
  2. Define clinically meaningful disease cohorts using standard cutoffs
  3. Discover which diseases cluster together in this Indian population
  4. Train machine learning models to predict each disease from lab values
  5. Make those predictions explainable with SHAP
  6. Deliver everything in an interactive Power BI dashboard
  7. Be portfolio-grade: clean code, good architecture, documented

WHY THIS PROJECT
----------------
- Most healthcare data-science portfolios rely on US/European datasets
  (MIMIC, CMS, eICU). NidaanKosha is the largest publicly available
  Indian lab dataset, so this fills a real gap.
- The user is a student building a capstone, so the project needed to
  demonstrate both technical depth and clear communication.
- We wanted it to be reproducible: anyone with the dataset and these
  scripts should be able to rebuild everything from scratch.

THE 11 PHASES WE PLANNED
-------------------------
Phase 0:  Set up Python environment (Anaconda, conda, packages)
Phase 1:  Scaffold project structure (folders, gitignore, README)

Phase 8:  XGBoost modeling per condition
Phase 9:  SHAP explainability (global + per-patient)

THE DATA LEAKAGE FIX (most important learning in this phase)
------------------------------------------------------------
WISH PROBLEM: First XGBoost run showed AUC = 1.000 for every condition.
              That is impossible in real data.
ROOT CAUSE:   The disease labels are deterministic functions of the lab
              values. For example, has_anemia is defined as
              hemoglobin < 12 (female) or < 13 (male). The model had
              hemoglobin as a feature, so it could perfectly predict
              the label by reading the threshold.
FIX:          Created LEAKY_FEATURES dict in modeling.py that maps each
              condition to the lab values used to define it. Excluded
              those features per-condition. Re-ran - got realistic AUCs.
LESSON:       AUC = 1.0 is a red flag, not a success. Always check if
              your features contain the answer.


PHASE 9: SHAP EXPLAINABILITY
----------------------------
WISH:    Explain WHY the model predicts a disease for a given patient.
         Not just "high risk" but "high risk BECAUSE creatinine is
         elevated AND BUN is high".
HOW:     Used shap.TreeExplainer on 4 conditions (CKD, Diabetes, Anemia,
         Liver Issue). Generated 3 figure types per condition:
           - Bar plot: top 15 global features by mean absolute SHAP
           - Beeswarm: feature value vs SHAP value (direction of effect)
           - Waterfall: one positive + one negative patient breakdown
EVIDENCE: 16 figures in reports/figures/ (4 conditions x 4 plot types).
          files: 04_shap_bar_*.png, 05_shap_beeswarm_*.png,
                 06_shap_waterfall_*.png
CRITICAL FIX: First SHAP run failed with "expected 48 features, got 41".
               Cause: the model was trained on the leakage-excluded
               feature subset, but SHAP was loading all 48 features.
               Fix: imported get_feature_columns(condition=...) from
               modeling.py so SHAP uses the SAME features the model saw.

================================================================================
PART 4: KEY LEARNINGS
================================================================================

1. THE 3-LAYER LAKEHOUSE PATTERN
   Bronze (parquet) -> Silver (DuckDB) -> Gold (MySQL/CSV).
   Don't load raw data to your serving database. Use a fast analytical
   engine for ETL and feature engineering, then ship only curated
   aggregates to the BI tool.

2. DATA LEAKAGE IS THE #1 ML TRAP
   If your features contain the answer, your model is cheating. Always
   check for AUC = 1.0 and audit whether labels are functions of features.

3. ALWAYS USE A FRESH PYTHON PROCESS PER PHASE
   exec() in the same process accumulates memory. subprocess.run()
   releases it on exit. For multi-step data pipelines, always subprocess.

4. NULL VALUES IN MEDICAL DATA ARE MEANINGFUL
   null != 0 != missing. In labs, null often means "not tested".
   Imputing away that signal biases the analysis.

5. WHEN A CONNECTOR FAILS, PIVOT FAST
   We lost 15 minutes fighting the MySQL .NET connector, then spent
   2 minutes exporting CSVs. The CSV path was simpler, faster, and
   gave the same end result. Don't sink cost into workarounds.

6. START WITH THE END IN MIND
   Every technical choice (which tables to load, which features to
   engineer, which visuals to build) was driven by what Power BI
   actually needs. The 6.8M raw rows were a stepping stone, not
   the destination.
